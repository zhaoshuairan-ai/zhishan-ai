# 智膳 AI · 比赛演示流程与 7 分钟讲稿

> 当前版本：智膳 AI · 全场景健康膳食管家  
> 演示目标：让评委在 7 分钟内看到「多模态识别 → 健康画像 → 智能配餐 → 知识证据 → 后台审核」的完整闭环，并确认系统不是静态页面或固定文案。

- [ ] 后端已启动，首页、智库、后台均能打开；
- [ ] 浏览器标签页顺序：首页 → 开始检测 → 分析结果 → 智膳智库 → 管理后台；
- [ ] 手机登录同一账号，准备展示跨设备同步；
- [ ] 网络异常时准备本地截图或录屏作为兜底。

## 三、逐段讲稿

### 0:00—0:40 开场

> 各位评委老师好，我们的作品是《智膳 AI》——一个面向家庭与个人的全场景健康膳食管家。
>
> 很多健康产品停留在“记录”：拍一张照片、记一个热量。但用户真正需要的是下一步：这个配料对我是否合适？家里现有食材怎么搭配？老人、儿童和慢病成员如何在同一顿饭里兼顾？
>
> 智膳 AI 做的事情，是把识别、解释、健康画像、配餐执行和人工审核组织成一个闭环。

### 0:40—2:00 多模态识别

>（打开“开始检测”，上传准备好的包装图片）
>
> 系统会先做图像识别与结构化。这里不是预置文案，而是真实的 OCR / 视觉模型链路：配料表、营养成分表、食品名称、日期等字段会被拆出来，并给出置信度。
>
> （指出低置信字段）
>
> 对不确定的字段，系统不会假装全对，而是标出来让用户校正。原始识别文本保留，校正结果单独保存，整个分析过程可追溯。
>
> 除了包装，系统也支持餐盘识别。餐盘场景更关注食物类别、份量与营养估算，而不是标签文字。

### 2:00—3:00 结果解读

>（进入分析结果页）
>
> 结果页分三层：第一层是结论与个性化提醒，第二层是配料与营养结构，第三层是证据与风险依据。
>
> 食品添加剂只解释用途与适用范围，不判定“有毒/有害”。真正的合规判断需要品种、使用范围、使用量和监管数据，不能只靠一张照片下结论。
>
> 营养成分会保留原始数值与单位，再换算到实际份量；知识库没有覆盖的内容明确标为未识别，不用模型猜测。

### 3:00—4:00 健康画像

>（打开健康画像）
>
> 通用建议为什么不够？因为它不知道“我是谁”。这里可以建立年龄、身高体重、活动量、减脂/控糖目标、高血压/糖尿病/高尿酸等慢病约束，以及过敏原和忌口。
>
> 画像不是展示字段，而是会进入后端约束：过敏原一票否决，慢病约束优先于口味偏好，孕期、老人、儿童有更保守的边界。
>
> 体检单也支持结构化解析，低置信字段要求用户确认，避免把识别错误直接变成健康建议。

### 4:00—5:10 智能配餐

>（进入家庭食材管家 / 配餐）
>
> 配餐 Agent 同时读取健康画像、冰箱库存、临期食材、天气、人数、时间和预算。
>
> 例如今天时间很紧，它会优先选择 20 分钟内能完成的菜；冰箱里有临期菠菜，它会优先消耗；家庭里有高血压成员，它会降低钠盐并给出替换建议；有人对花生过敏，含花生方案直接排除。
>
> 输出不是一段泛泛的建议，而是菜品、食材、份量、步骤和采购清单。用户执行后可以扣减库存，形成“识别—规划—执行”的闭环。

### 5:10—5:50 智膳智库

>（打开智膳智库）
>
> 智膳智库只展示“已发布且已核验”的内容，数量和分类都来自后端真实统计，而不是前端写死。
>
> 每条知识包含来源、适用范围、版本和核验状态；检索结果会作为 RAG 证据进入模型上下文。模型必须基于证据回答，低置信或没有召回时拒绝给出确定性结论。
>
> 这就是我们和通用聊天机器人最大的区别：不是“说得像”，而是“说得出依据”。

### 5:50—6:30 后台审核

>（打开管理后台）
>
> AI 生成内容不会直接进入 C 端。后台可以按待审核、已发布、已下架管理；审核员能看到原文、结构化字段、AI 结论与引用，并进行修正。
>
> 每一次审核都会写入审计日志；修正样本回流到评测集，形成 Human-in-the-loop 数据飞轮。模型不是一次性训练完就结束，而是在真实使用中持续校准。

### 6:30—7:00 收尾

> 最后说明边界：系统只读取用户提供的图片和文字，不做实验室检测，不判断微生物、农残、重金属，也不替代医生诊断。
>
> 技术上，前端是 Vue 3 + TypeScript，后端提供 REST/SSE 接口，AI 层使用 DeepSeek-chat 与 Qwen-VL 系列，知识层使用 GB 2760 与平台审核知识做 RAG，配餐层使用动态 Prompt 注入健康画像、天气、库存与预算。
>
> 我们的创新点不是“换一个更大的模型”，而是把多源数据、证据链、人工审核和家庭协同组织成可持续的健康决策系统。谢谢各位评委老师。

## 四、演示动线建议

1. **首页只讲定位**：一句话说清“识别—理解—规划—执行”。
2. **识别环节主动指出低置信字段**：这是可信设计的加分项。
3. **结果页不要逐条念**：重点讲个性化提醒、营养结构和证据来源。
4. **画像环节讲“约束如何生效”**：不要只展示表单。
5. **配餐环节讲一个冲突消解案例**：例如“高血压 + 临期菠菜 + 20 分钟”。
6. **智库环节讲统计口径**：只展示已发布且已核验，数量来自后端。
7. **后台环节讲数据飞轮**：审核不是附属功能，而是模型进化入口。

## 五、异常兜底

| 情况 | 应对 |
| --- | --- |
| 网络断开 | 使用本地已启动服务与预置记录，先演示识别与智库 |
| OCR 失败 | 说明图片质量影响，改为手动校正或使用预置记录 |
| 模型超时 | 系统会降级到规则/本地知识，顺势讲降级链路 |
| 手机连不上 | 切回电脑演示，手机环节改为展示已同步截图 |
| 时间被压缩 | 只演示：识别结果 → 健康画像约束 → 配餐方案 → 后台审核 |

## 六、评委常见问题

**Q1：和通用聊天机器人有什么区别？**

> 通用模型主要依赖参数记忆；智膳 AI 有真实识别链路、结构化健康画像、RAG 证据检索、规则校验和人工审核。结论要能回到来源，低置信会拒答。

**Q2：AI 会不会胡说？**

> 会，所以我们做了多层控制：知识检索、Prompt 约束、JSON Schema 校验、引用一致性检查、低置信拒答和人工复核。食品安全场景不能只靠生成。

**Q3：为什么需要后台审核？**

> 高风险领域需要人类最终裁决。审核修正会回流为评测样本，形成数据飞轮；同时审计日志保证每一步可追溯。

**Q4：数据与隐私怎么处理？**

> 密钥只在服务端环境变量中读取；密码使用哈希存储；健康数据按账号隔离；上传文件做类型、大小与路径校验；公开仓库不提交 `.env`、数据库和用户上传图片。

**Q5：为什么用 SQLite？**

> 比赛演示阶段 SQLite 零配置、便于复现；数据访问层使用 SQLAlchemy，生产可迁移 PostgreSQL，并补充缓存与对象存储。

## 七、一页式项目介绍

**智膳 AI** · 全场景健康膳食管家

- **一句话**：拍一张包装或餐盘照片，完成识别、解释、健康画像约束与三餐方案。
- **核心能力**：多模态识别｜RAG 证据解释｜健康画像｜智能配餐｜家庭库存｜后台审核。
- **可信设计**：来源引用｜低置信拒答｜人工审核｜审计日志｜敏感配置不下发前端。
- **技术栈**：Vue 3 + TypeScript + Vite + Element Plus + ECharts｜Flask + SQLAlchemy + SQLite｜DeepSeek-chat / Qwen-VL｜SSE。
- **边界**：不做实验检测，不判定添加剂“有毒”，不构成医疗诊断。
